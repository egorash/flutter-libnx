## 2. Звук: `audioplayers`

### 2.1 Протокол (прочитан в пакете, не додуман)

- MethodChannel `xyz.luan/audioplayers` (`audioplayers_platform_interface-7.1.1/lib/src/audioplayers_platform.dart:32`).
  Методы: `create`, `dispose`, `release`, `play`/`pause`/`resume`/`stop`, `seek`,
  `setVolume`, `setBalance`, `setPlaybackRate`, `setReleaseMode`, `setPlayerMode`,
  `setAudioContext`, `setSourceUrl`, `setSourceBytes`, `getCurrentPosition`,
  `getDuration`, `emitLog`, `emitError`. В аргументах всегда `playerId`.
- EventChannel **на каждый игрок**: `xyz.luan/audioplayers/events/<playerId>`
  (`audioplayers_platform.dart:242`). События — словари
  `{"event": "audio.onPrepared", "value": true}`, `audio.onDuration`,
  `audio.onComplete`, `audio.onSeekComplete`, `audio.onLog`.
- MethodChannel `xyz.luan/audioplayers.global` и EventChannel
  `xyz.luan/audioplayers.global/events` (`global_audioplayers_platform.dart:18`).

### 2.2 Условие, без которого звук не «заработает», а «зависнет»

`AudioPlayer.play()` → `_completePrepared()` ждёт события `onPrepared`
(`audioplayer.dart:358-372`). Таймаут — **30 секунд**
(`audioplayer.dart:22`). Если EventChannel не отвечает, каждый вызов `play()`
висит полминуты. Значит событие `audio.onPrepared` с `value: true` —
обязательная часть контракта, а не украшение.

### 2.3 Откуда берутся байты

Для `AssetSource` Dart-сторона сама читает ассет через `rootBundle` и
**записывает во временный файл**: `${getTempDir()}/$cacheId/$fileName`
(`audio_cache.dart:100-106`). `getTempDir()` — это `path_provider`, а он в
порту реализован: `/switch/flutter_apps/romashka_game/tmp`
(`plugins_horizon.cpp:92`). Дальше приходит `setSourceUrl(..., isLocal: true)`
с этим путём.

Отсюда хорошая новость: **нативной части достаточно читать обычный файл с
SD-карты** через существующий слой `posix_compat`. RomFS-обход не нужен.

### 2.4 Нагрузка — отсюда архитектура

В игре 15 коротких звуков в пулах (`audio_service.dart:239-253`), сумма
размеров пулов — **30**, плюс `FlameAudio.bgm` — итого до **31 одновременного
игрока**. Все 16 файлов — MP3 (`assets/audio/*.mp3`), 3.7 МБ.

Вывод: «декодер на игрока» не годится — 31 поток декодирования на
четырёхядерной консоли, где порт уже наступал на границы числа потоков.
Нужен **один аудио-поток и микшер**:

- голос = состояние minimp3 + кольцевой буфер PCM;
- поток ждёт кадры `audrenWaitFrame()`, для каждого активного голоса
  добирает декодированные кадры, суммирует, отдаёт в `audren`;
- MethodChannel-обработчики только управляют списком голосов с
  платформенного потока (данные защищены короткой блокировкой).

Число потоков: **+1** (аудио), плюс **+1** на геймпад (см. §3).

### 2.5 Декодер: развилка

| | minimp3 (вендорим) | FFmpeg (уже линкуется) |
|---|---|---|
| Объём | один заголовок ~80 КБ | уже в NRO ради media_kit |
| Инициализация | нет | поиск декодера, контекст |
| Память | минимальная на голос | заметная на голос |
| Форматы | только MP3 | всё |
| Риск | вендорим чужой код (~1000 строк) | тяжёлый API, конфликты символов с media_kit |

Рекомендация: **minimp3** — ассеты игры на 100% MP3, а независимость от
media_kit того стоит. FFmpeg оставить запасным вариантом, если появятся
ogg/wav.

**Решение (2026-10-16): minimp3.** Ассеты игры — 16 файлов MP3, вокапом до 31
источника, поэтому вес одного голоса решает. FFmpeg остаётся запасным
вариантом на случай появления ogg/wav.

### 2.6 Блоки работ

- [ ] **A1.** `audren`: инициализация 48 кГц / стерео / 16 бит, отдельный поток,
      кадр за кадром, корректный выход. Проверка: тишина без ошибок в логе.
- [ ] **A2.** Голос: minimp3 + кольцевой буфер, 31 голос, микширование с
      ограничением по громкости.
- [ ] **A3.** MethodChannel `xyz.luan/audioplayers`: полный набор методов;
      `setSourceUrl` открывает файл через `posix_compat`.
- [ ] **A4.** EventChannel на игрок: `onPrepared` (обязательно), `onDuration`,
      `onComplete`, `onSeekComplete`. Имена каналов динамические — в реестре
      нужен **префиксный** поиск, а не точное совпадение.
- [ ] **A5.** `xyz.luan/audioplayers.global` — заглушки (resume/stop контекста).

### 2.7 Риски

- 30 с таймаута на каждый `play()`, если событие не уходит — самая дорогая
  ошибка; лечится проверкой в A4.
- Переполнение кольцевого буфера при перегрузке (много одновременных
  источников) — нужен аккуратный отсчёт «сколько декодировать».
- `audren` требует аккуратного порядка `RequestUpdateAudioRenderer` /
  `StartAudioRenderer`; ошибка здесь — тишина без внятного сообщения.
- Потоки: +1 аудио, что при уже плотной картине потоков порта требует
  проверки на железе.

## 3. Геймпад: `gamepads`

### 3.1 Ключевой факт, который объясняет «не тот маппинг»

`GamepadNormalizer` выбирает таблицу по `defaultTargetPlatform`
(`gamepads-0.1.12/lib/src/gamepad_normalizer.dart:78`). А `defaultTargetPlatform`
на Switch равен **linux**, потому что `Platform.operatingSystem` у нас
возвращает `"linux"` — это сделано нашим же патчем
(`dart/runtime/bin/platform.h:37`), иначе Flutter не знает платформу и
бросает исключение при создании `FocusManager`.

Значит игра возьмёт **LinuxMapping**, и нативная часть обязана слать ключи
**в SDL-стиле, числами** — не `KEYCODE_BUTTON_A`, не `a`.

### 3.2 Таблица соответствия

Кнопки (`gamepads_controller_database.dart:141`, порядок Xbox):

| libnx | ключ | смысл |
|---|---|---|
| `HidNpadButton_A` | `"0"` | A |
| `HidNpadButton_B` | `"1"` | B |
| `HidNpadButton_X` | `"2"` | X |
| `HidNpadButton_Y` | `"3"` | Y |
| `HidNpadButton_L` | `"4"` | LB |
| `HidNpadButton_R` | `"5"` | RB |
| `HidNpadButton_Minus` | `"6"` | Back |
| `HidNpadButton_Plus` | `"7"` | Start |
| `HidNpadButton_Screenshot` | `"8"` | Home |
| `HidNpadButton_StickL` | `"9"` | L3 |
| `HidNpadButton_StickR` | `"10"` | R3 |

Оси (`controller_database.dart:154`):

| libnx | ключ | диапазон | примечание |
|---|---|---|---|
| `sticks[0].x` | `"0"` | −32768..32767 | левый стик X |
| `sticks[0].y` | `"1"` | −32768..32767 | левый стик Y, **инверсия** |
| ZL | `"2"` | — | как триггер |
| `sticks[1].x` | `"3"` | −32768..32767 | правый стик X |
| `sticks[1].y` | `"4"` | −32768..32767 | правый стик Y |
| ZR | `"5"` | — | как триггер |
| D-Pad лево/право | `"6"` | ±32767 | `dpadAxes['6'] = true` |
| D-Pad вверх/вниз | `"7"` | −32767 = вверх | `yAxisInverted = true` |

Значения `sticks` у libnx — `s32` в диапазоне ±32768, то есть масштабировать
не нужно. **D-Pad у libnx — кнопки**, а LinuxMapping ждёт ось-шляпу: значит
нативная часть синтезирует ось `"6"`/`"7"` (0 — отпущено, ±32767 — нажато).

`vendorId`/`productId` можно не слать: `LinuxMapping` при `bestEffort`
подставляет `ControllerDatabase.defaultMapping` (`linux_mapping.dart:44-47`).

## 6. Грабли libnx, на которые наступили (проверено по исходникам)

Три ошибки стоили больше времени, чем весь остальной код вместе взят, и
все три выглядели как «плагин не работает». Собраны здесь, потому что
очевидного объяснения у них нет — лечится только чтением `nx/source`.

### 6.1 `active_id_mask` не покрывает встроенные джой-коны

`nx/source/runtime/pad.c`:

```c
void padInitializeWithMask(PadState* pad, u64 mask) {
    memset(pad, 0, sizeof(*pad));
    pad->id_mask = mask & 0xff;                    // только игроки No1..No8
    pad->read_handheld = (mask & (1UL << HidNpadIdType_Handheld)) != 0;
}
```

`active_id_mask` — поле типа `u8`, и наполняют его только по `id_mask`, то
есть исключительно по игрокам 1–8. Встроенные джой-коны в портативном
режиме идут отдельной веткой:

```c
if (pad->read_handheld) {
    if (hidGetNpadStatesHandheld(...) && (state.attributes & HidNpadAttribute_IsConnected)) {
        pad->active_handheld = true;               // а active_id_mask остаётся 0
        _padUpdateWithCommonState(pad, &state);    // кнопки при этом приходят
    }
}
```

**Признак:** контроллер живой, вибрация инициализируется, `listGamepads`
отдаёт идентификатор — а событий нет вообще. В доке такой код работал бы,
в руках нет.

**Лечение:** `connected = pad_.active_id_mask != 0 || pad_.active_handheld;`

### 6.2 `start_sample_offset` / `end_sample_offset` — это байты

`AudioRendererWaveBuf` ждёт смещения **в байтах от `data_raw`**
(см. `audren-simple`: `end_sample_offset = sample_bin_size / 2`). Если
`data_raw` уже указывает на начало слота, смещения должны быть `0` и
`записанные байты`.

Ошибочный вариант — считать их номерами отсчётов слота:

```c
buf.start_sample_offset = s * kSlotOutSamples;   // неверно
```

**Признак:** слот 0 играет первую половину, последние слоты читают за
пределами своего буфера. Звук либо отсутствует, либо идёт мусором.

### 6.3 Возвращаемые значения `audrv*` нельзя игнорировать

`audrvVoiceAddWaveBuf` возвращает `bool` и молча отказывает при выравнивании
по `AUDREN_BUFFER_ALIGNMENT` (0x40) и при занятом буфере; `audrvVoiceInit`
может отказать из-за нехватки свободных каналов (`num_voices` — это счёт
каналов, а не голосов). Пока возвраты не проверялись, в протоколе не было
ни строчки, по которой можно было отличить «наш код молчит» от «сервис не
принял».

**Что стоит проверять по возврату и писать в лог:**

| Вызов | Что означает отказ |
|---|---|
| `audrvVoiceInit` | кончились каналы либо голос занят |
| `audrvVoiceAddWaveBuf` | буфер выровнен не по 0x40 либо ещё не `Done` |
| `audrvVoiceGetPlayedSampleCount` | сколько отсчётов сервис реально отдал |
| `audrvVoiceGetVoiceDropsCount` | сколько буферов сервис сбросил |

### 6.4 Отпускание терялось: два независимых хранилища состояния

`LastValue` и `Remember` держали **по своему** `static std::vector`.
`Remember` писал в один, `LastValue` читал из другого, который никто не
заполнял. Значит `LastValue()` всегда отдавал `0`, и вся логика
«отправлять только изменения» работала наоборот:

- **отпускание не отправлялось никогда** — `0` против `0` это равенство,
  событие не создавалось; игра считала кнопку залипшей до конца прогона,
- нажатая кнопка уходила в поток на каждом опросе (60 Гц),
- ось, вернувшаяся в ноль, то же самое — молчала вместо отпускания.

В логе это выглядело как `80 Tasten und 510 Achsenbewegungen` за три
секунды и полное отсутствие `value=0`. Игра с залипшими кнопками требует
«комбинаций», чтобы что-то сработало: сначала нажать, потом отжать
другим нажатием, чтобы抵消 залипание.

**Лечение:** одно хранилище, `Remember` пишет через `LastValue`.

### 6.5 Раскладка совпадает с `ControllerDatabase.defaultMapping`

Проверено по пакету `gamepads` 0.1.12
(`lib/src/mappings/controller_database.dart`):

| Ключ | Кнопка | Ось |
|---|---|---|
| `0`..`10` | a, b, x, y, leftBumper, rightBumper, back, start, home, leftStick, rightStick | — |
| `0`..`5` | — | leftStickX, leftStickY, leftTrigger, rightStickX, rightStickY, rightTrigger |
| `6`, `7` | — | ось шляпы D-Pad: `6` — X, `7` — Y |

Плюс `yAxisInverted: true` и `stickRange`/`triggerRange` = `(-32768, 32767)`.

Ось `6`/`7` не обязана быть кнопкой: в `gamepad_normalizer.dart` для
аналогового события, если `normalizeAxis` ничего не вернул, вызывается
`normalizeDpadAxis`. Поэтому синтез D-Pad осью — правильный ход, а не
обходной.

**Важно:** таблица из `examples/ui_app/source/main.cpp` здесь
неприменима. `ui_app` отправляет клавиатурные события с кодами SDL
(`SDLK_*`) в `FlutterEngineSendKeyEvent`, и его Dart слушает
`HardwareKeyboard`. У `romashka_game` ввод идёт через пакет `gamepads`,
и там другое пространство имён: числовые строки указывают и кнопки, и
оси, причём различаются они только типом события.

### 6.6 Главная причина тишины: аудиоцикл не был темпирован

Дословно из протокола прогона:

```
[  79 ms] Audio: Stimme 0 -> 2304 Abtastwerte in Slot 0
[ 605 ms] Audio: Stimme 0 zu Ende, 926208 Abtastwerte gesamt
```

926208 отсчётов — это **19 секунд** музыки, декодированные за полсекунды.
Рендерер отдаёт звук в реальном времени, а мы вливали в него данные с
скоростью процессора: голос набивал четыре буфера быстрее, чем сервис их
успевал отдать.

Причина в ожидании кадра. `audrenWaitFrame()` ждёт **системное** событие
(счётчик кадров изображения, 60 Гц) и наш цикл оно не ограничивало.
Правильный примитив задокументирован в самом `audren.h`:

```c
/// Returns event that is signalled on new frame (autoclear=true).
Event* audrenGetFrameEvent(void);
```

Ожидание на нём даёт ровно тот темп, который задаёт сервис:
`AUDREN_TIMER_PERIOD_MS = 5.0`, `AUDREN_SAMPLES_PER_FRAME_48KHZ = 240`,
то есть 200 кадров в секунду по 240 отсчётов.

**Лечение:**

```cpp
const Handle frame_event = audrenGetFrameEvent()->revent;
waitSingleHandle(frame_event, 100'000'000ULL);   // таймаут - только ради выхода
```

Таймаут в 100 мс — исключительно чтобы `Shutdown` не висел: рендерер
сигналит каждые 5 мс, так что ожидание всегда срабатывает по событию.

Размер слота тоже взят кратным кадру: `kSlotOutSamples = 2400`
(10 кадров = 50 мс) вместо 2304.

### 6.7 Лог не показывал ровно то, что ломалось

`gamepads: Tasten und Achsenbewegungen gesendet` ограничивался **40
событиями на весь прогон**. За первые две секунды это исчерпывалось, и
дальше протокол был слепым: не видно ни отпускания кнопок (`value=0`),
ни D-Pad (`Achse key=6`), то есть ровно той части, где всё и ломалось.

Лимит перенесён на каждый ключ отдельно: по шесть событий на ключ.

### 6.8 D-Pad через пакет gamepads самоуничтожается

Разбор цепочки `gamepads` 0.1.12 + `romashka_game` показал, что кнопки
«в комбинациях» - это не подбор, а вполне определённый дефект.

`LinuxMapping.normalizeDpadAxis` возвращает на каждое событие оси **обе**
кнопки, включая не нажатую:

```dart
return [
  NormalizedButton(GamepadButton.dpadLeft,  value < 0 ? 1.0 : 0.0),
  NormalizedButton(GamepadButton.dpadRight, value > 0 ? 1.0 : 0.0),
];
```

Игра применяет их по порядку в **одну** переменную:

```dart
case GamepadButton.dpadLeft:  setPadDpad(pressed ? -1 : 0);
case GamepadButton.dpadRight: setPadDpad(pressed ?  1 : 0);
```

| Нажато | События | Итог `_padDpadAxis` |
|---|---|---|
| влево | dpadLeft=1, затем dpadRight=0 | `-1`, сразу `0` — **нет движения** |
| вправо | dpadLeft=0, затем dpadRight=1 | `0`, затем `1` — **работает** |

Влево гасит сам себя. То же с вертикалью, но там у игры нет случая
`dpadUp`, поэтому `dpadDown` как последнее событие выигрывает.

**Обойти с нашей стороны нельзя:**

- в `ControllerDatabase.defaultMapping` у D-Pad нет кнопочных ключей -
  только `dpadAxes: {'6': true, '7': false}`, то есть ось;
- при событии-кнопке `normalizeDpadAxis` вызывается лишь если ключа нет в
  `buttons`, а ключи `6` и `7` там есть (`back`, `start`).

Единственный путь - ось `6`/`7`, а она всегда отдаёт обе кнопки.

**Лечение:** вернуть клавиатурный путь (`FLUTTER_LIBNX_PAD_KEYBOARD=1`).
Там приходят настоящие раздельные события клавиш-стрелок. То, что его
отключили в `0edf840`, было вызвано залипанием отпускания - дефектом
`LastValue`/`Remember` из §6.4, который с тех пор исправлен.

### 6.10 armGetSystemTick() отдаёт тики, а не наносекунды

```c
static inline u64 armGetSystemTick(void) {
    __asm__ __volatile__ ("mrs %x[data], cntpct_el0" : [data] "=r" (ret));
    return ret;     // <- тики; частота на Horizon 19,2 МГц
}
```

Один тик = 52,08 нс. Мы делили на `1'000'000`, считая результат
миллисекундами, и получали **занижение в 52 раза**.

Ошибка дорого стоила дважды, потому что оба раза выглядела как
исправная работа:

1. **Геймпад.** Период опроса был записан как `1000000000 / 60` и
   сравнивался с тиками: `16'666'666 / 19'200'000 = 0,868` секунды между
   опросами вместо `16,7 мс`. Кнопка, нажатая короче окна, просто
   терялась. Отсюда ровно наблюдаемое:

   | Действие | Почему результат такой |
   |---|---|
   | кнопки по очереди | нажатие короче 868 мс, попадает в опрос через раз |
   | кнопочный шторм | хоть одна из десяти нажата в момент опроса |
   | «подгадывать время» | буквально подгонка под окно опроса |

   При этом в протоколе стояло `Abfrage laeuft, 60 Hz` - цифра из
   константы, а не из измерения.

2. **Время в протоколе.** Строка `785 ms` означала **41 секунду** реального
   времени. Шаг между нажатиями `17 ms` - это **885 мс**, обычный
   человеческий темп. Логи выглядели обрезанными и это подтверждалось
   срезом на середине серии, но ничего не было обрезано: время просто
   показывалось неверно.

**Лечение:** `embedder/include/flutter_libnx/tick_clock.h`. Внутри кода
только тики; наносекунды остаются исключительно там, где их требует
ядро (таймауты `waitSingleHandle`). Строка `60 Hz` заменена вычислением
из частоты счётчика.

### 6.11 Главная причина тишины: не было выхода к устройству

В эталоне `audren-simple` есть строка, которой не было ни здесь, ни в пробе:

```c
static const u8 sink_channels[] = { 0, 1 };
audrvDeviceSinkAdd(&drv, AUDREN_DEFAULT_DEVICE_NAME, 2, sink_channels);
```

`audrvDeviceSinkAdd` делает две вещи:

```c
d->in_sinks[id].type = AudioRendererSinkType_Device;
d->in_sinks[id].is_used = true;
d->in_sinks[id].node_id = AUDREN_NODEID(3,id,0);
```

а `_audrvInitConfig` из `driver.c` заполняет **только `etc`-копию**
массива стоков:

```c
d->in_sinks = (AudioRendererSinkInfoIn*)(d->in_mixes+d->config.num_mix_objs);
for (int i = 0; i < d->config.num_sinks; ++i)
    d->etc->sinks[i].next_free_splitter = ...;      // это etc, не in_sinks
```

`d->in_sinks[0]` остаётся обнулённым: `type = Invalid`, `is_used = false`.
Конечная шина считает - и **некуда**. Отсюда картина, которая сбивала с
толку пять раундов подряд:

```
unsere 9216, abgespielt 0, verworfen 0
```

Данные доходят, слоты в очереди у сервиса, отброшенных буферов ноль -
а на выходе ноль. Рендерер работает, просто результат некому принять.

**Признак, по которому это узнаётся:** при живых данных и нулевых
`played_sample_count` менять микшер бессмысленно - виновата не
маршрутизация голоса, а отсутствие адресата у конечной шины.

### 6.12 Что дала проба `hw_probe`

Прогон без Flutter и Dart показал две вещи разом.

**Ввод исправен.** Маски приходят точно по значениям `HidNpadButton_*` из
`hid.h`, в портативном режиме (`Stil 0x02`), псевдокнопки стиков помечены
и совпадают с показаниями стиков. Раскладка была верной с самого начала -
все пять раундов это не трогали.

**Темп аудиоцикла был нормальным.** Я считал, что 19 секунд музыки
декодировались за 605 мс и цикл шёл со скоростью процессора. На деле это
31 секунда реального времени (§6.10) - обычный темп. Правка на
`audrenGetFrameEvent()` была лишней, `audrenWaitFrame()` из эталона
возвращён.

### 6.13 Кнопки и оси делили одну таблицу состояния

Ключи пересекаются: кнопки шлют `"0".."10"`, оси тоже `"0".."7"`. При
общей таблице `LastValue` одно движение стика портило обе части порта:

```cpp
SendAxis("0", 32367);          // пишет LastValue("0") = 32367
// ...та же итерация, проверка кнопки A:
if (LastValue("0") != 0.0) {   // 32367 != 0 -> "A нажата"
```

Из этого вышли все три наблюдавшихся симптома:

| Наблюдение | Как получалось |
|---|---|
| стик отпущен, движение продолжается | `SendAxis("0", 0)` сравнивал ноль с нулём (в ячейке лежало состояние кнопки) и молчал; игра вечно видела 32367 |
| прыжок только после движения стиком | движение стика приравнивалось к нажатию A |
| прыжок гасит движение | нажатие A обнуляло ячейку `"0"`, и ось замирала |

Состояния разведены на две таблицы: `LastButtonValue` и `LastAxisValue`.
Ключи у осей и кнопок — разные пространства имён, и хранить их вперемешку
нельзя.

Попутно значение оси в зоне покоя приводится к нулю. Иначе стик, который
физически вернулся в центр, продолжает числиться отклонённым: значения
меньше порога `SendAxis` отбрасывает молча, и последнее отправленное
значение остаётся в игре навсегда.

### 6.14 Ресемплинг терял 8,1 % сигнала

Число выходных отсчётов совпадало с числом входных:

```
Audio: Quelle music_theme.mp3, 44100 Hz, ~21000 ms
Stimme 0 zu Ende, 926287 Abtastwerte          <- 926287 ≈ 926100 = вход
```

При правильном ресемплинге должно быть `926100 × 48000/44100 = 1 008 000`.

**Механика.** На порцию бралось 2400 входных отсчётов, а выходная
ёмкость тоже 2400. Ресемплинг доходил до `2400 × 147/160 = 2205` и упирался
в ёмкость, поэтому перенос получался `2205 - 2400 = -195`. Дальше:

```cpp
voice.resample_carry = position - (total - 1);
if (voice.resample_carry < 0.0) {
  voice.resample_carry = 0.0;                // <- теряем 195 отсчётов
}
```

Обнуление выбрасывало 195 отсчётов из 2400 — 8,1 % сигнала — на каждой
порции. На слух это ровно два симптома сразу:

- данные 44,1 кГц игрались как 48 кГц: на 8,8 % быстрее и на ~1,2 полутон
  выше — **«сжатый» звук**;
- каждые 54 мс пропадал кусок длиной 4,4 мс — **прерывистость**.

**Лечение:**

1. Запрос декодеру ровно на одну порцию: `kSlotInSamples = 2400 × 44100 /
   48000 = 2205`. Перенос при этом равен нулю, обрезать нечего.
2. Позиция в сотых долях отсчёта (`carry160`, шаг 147 при масштабе 160), а не
   в `double`: ошибка накапливается за сотни тысяч отсчётов.
3. Перенос при нехватке входа сохраняется, а не обнуляется; обнуляется
   только когда данных меньше, чем нужно для одного выходного отсчёта.

Проверено на хосте на реальном сигнале (синус 440 Гц, 926100 отсчётов):

```
вход   926100 отсч. = 21.000 с при 44100
выход 1008000 отсч. = 21.000 с при 48000
расхождение         = 0.000 %
перенос в конце     = 0/160
```

### 6.15 Выход по Plus перехватывал кнопку паузы

В общем раннере стояло:

```cpp
if (padGetButtonsDown(&platform.pad()) & HidNpadButton_Plus) break;
```

Это не ограничение консоли, а наше собственное решение, причём вредное.
Что резервирует сама система:

| Кнопка | Что делает | Видна ли процессу |
|---|---|---|
| HOME | выход в hbmenu | нет: константы `HidNpadButton_Home` в libnx не существует, кнопку перехватывает ОС |
| Capture | альбом | так же не видна |
| Plus | обычная кнопка | да, приходит как `0x00000400` (видно в `hw_probe`) |

Выход по HOME уже работает без всякого кода с нашей стороны:
`appletMainLoop()` возвращает `false`, когда система запрашивает
завершение.

`romashka_game` вешает паузу на `GamepadButton.start`, а это в
`ControllerDatabase.defaultMapping` ключ `"7"` — то есть **Plus**. С
собственной проверкой выхода первое же нажатие на паузу закрывало игру.

Проверка убрана. Раннер теперь завершается только по HOME, как на обычной
консоли. Блокировки выхода (`appletLockExit`) в проекте нет, значит
15-секундного таймаута принудительного завершения тоже нет - уборка после
цикла выполняется полностью.

### 6.16 Голос брался на `create`, а не на `play`

```dart
class AudioPlayer { ... _create(); }     // audioplayer.dart:172
```

`create` приходит из **конструктора** `AudioPlayer` - то есть на каждый
созданный плеер, включая тот, который никогда не зазвучит. Голос
выделялся именно там:

```cpp
if (method == "create") {
  const int voice = AllocateVoice();     // <- голос занимается сразу
  Players()[player] = voice;
```

Игра держит пул из 30 плееров плюс фоновую музыку и создаёт новые
поверх. Во втором прогоне подряд:

```
нехватка голосов: 265
всего игроков:    297
```

**265 из 297** — то есть почти каждый звук начинался с того, что
прерывался чужой, ещё звучавший. Ровно это и есть «звук очень плохо»,
когда пропускная способность при этом идеальна.

**Лечение:**

1. `create` голоса не занимает: в таблице значится `-1` = «голоса нет».
2. Голос берётся в `setSourceUrl` / `setSourceBytes` — туда приходит и
   ассет, то есть это единственная точка, где ресурс действительно нужен.
3. По завершении (`audio.onComplete`) голос **сразу возвращается** в пул.
   Иначе Dart держит плееры живыми между звуками и пул снова забьётся.
4. Поиск жертвы при нехватке больше не заглядывает в записи со значением
   `-1`: раньше туда передавалось `flutter_libnx_audio_voice_idle(-1)`,
   то есть индекс `-1` в массиве голосов.

**Проверка в протоколе:** строка `audioplayers: Player ... -> Stimme N`
теперь появляется на `setSource`, а не на `create`, а
`keine freie Stimme` должна исчезнуть совсем.

### 6.17 Перестановка голоса на `setSource` сломала звук полностью

Лог показал ноль и ноль:

```
Player ... -> Stimme: 0
Audio: Quelle:        0
```

Причина в порядке обработки. Ранний выход для игрока без голоса стоял
**до** блока `setSourceUrl`:

```cpp
int voice = VoiceOf(player);
if (voice < 0) {                      // <- create теперь даёт -1
  Respond(engine, message, BenignValueFor(method));
  return true;                        //    <- setSource сюда и попадал
}
...
if (method == "setSourceUrl" || ...) { ... }   // сюда уже не доходили
```

Раньше это было безобидно: голос давался на `create`, поэтому к
`setSource` он всегда был. Стоило перенести выделение голоса на
`setSource` — и блок оказался ниже раннего выхода, то есть недостижимый
для всех, у кого голоса ещё нет, то есть для всех.

**Правило, которое здесь действует:** блок, который сам выделяет ресурс,
обязан стоять **до** проверки «ресурса нет».

### 6.18 Голос освобождался, пока звук ещё не доигран

`mp3dec_ex_read` возвращает 0, когда файл декодирован целиком. Но у
голоса в рендерере в этот момент лежит около 170 мс уже готового звука.
Освобождение голоса на этом месте вызывает `audrvVoiceStop` и **обрезает
хвост**.

Поэтому `audio.onComplete` теперь отправляется не там, где декодер
дочитал файл, а там, где рендерер действительно всё отдал:

```cpp
if (voice.finished) {
  if (!voice.reported_done && !audrvVoiceIsPlaying(&driver_, i)) {
    voice.reported_done = true;
    events_.push_back({i, false});
  }
  continue;
}
```

`audrvVoiceIsPlaying` возвращает истину, пока у голоса есть непустая
очередь буферов, — то есть это ровно признак «звук ещё звучит».

Попутно убрана гонка: `events_` — это `std::deque`, и в него писали из
аудиопотока **без** мьютекса, тогда как читает из него главный поток под
замком. Теперь обе записи под замком.

### 6.19 Потоки хранились по голосу, а не по игроку

Симптом был обманчивым: **звук работал**, а в протоколе стояло 191
`TimeoutException` на `AudioPlayer._completePrepared`.

```cpp
std::map<int, EventChannel>& Streams();     // ключ - голос
...
it = streams.emplace(voice, EventChannel(channel_name)).first;
```

`EventChannel` создаётся с именем канала, а оно строится из **id
игрока**. Таблица же адресована по **голосу**. Пока голос давался на
`create` и жил до `dispose`, совпадение держалось само собой. С переносом
выделения на `setSource` (голос появляется, потом возвращается в пул) у
одного игрока за жизнь сменилось несколько голосов — и на каждое
создавался новый `EventChannel` для того же имени канала. Подписка Dart
осталась на старом объекте, новое событие уходило в никуда.

Плюс при завершении я добавил `Streams().erase(voice)` — это ломало
подписку сразу и окончательно.

**Лечение:** `Streams()` и `PendingPrepared()` ключуются по `playerId`.
Поток принадлежит игроку; голос — внутреннее дело реализации. По
завершении голос возвращается в пул, **поток не трогается**: он должен
пережить любое число звуков.

Обработчик потока больше не требует, чтобы у игрока уже был голос:
подписка приходит раньше первого звука, и это нормально.
