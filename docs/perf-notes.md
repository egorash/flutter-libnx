# Производительность и шум логов (Спринт 3, H/I)

Рабочие заметки по блоку **H** плана `docs/infra-plan.md`: обзор «горячих»
путей, список подозрительных логов и замеры. Служат входом для блока **I**
(снижение шума).

**Методика:** локальный анализ кода + данные из логов, снятых с железа
(`build-logs/my_nexus.log`, `.alt`, прогон 2026-10-11). Цель — **выявить**, а
не оптимизировать преждевременно.

---

## H1. Обзор горячих путей

### H1.1 Главная петля (250 Гц)

`examples/<app>/source/main.cpp`:

```
while (appletMainLoop()) {
  platform.PollEvents();
  SendTouchEvents(...); UpdateVirtualCursor(...); SendKeyEvents(...);
  task_runner.RunExpiredTasks(engine);        // платформенные задачи движка
  flutter_libnx_media_kit_video_pump(engine);
  svcSleepThread(4'000'000);                  // 4 ms → 250 итераций/с
}
```

Вся платформенная работа (ввод + платформенные задачи движка) идёт в одном
темпе 250 Гц. UI и растеризация — на собственных потоках движка. **В самой
петле логов нет** — это правильно: при `fflush` на каждую строку любая строка
в тике означала бы запись на SD 250 раз/с.

### H1.2 TaskRunner (`embedder/src/engine/task_runner.cpp`)

`RunExpiredTasks` вызывается каждый тик и на каждом вызове заводит **две
локальные** `std::vector` (`due` и `remaining`, с `reserve`). При пустой
очереди аллокаций нет (пустые векторы не выделяют память); при непустой —
аллокации каждый тик. Элементы копируются, а не перемещаются.

- **Оценка:** низкий приоритет. Платформенная очередь обычно короткая; выигрыш
  от переиспользования буферов невелик.
- **Идея (не срочно):** держать `due`/`remaining` членами класса и
  переиспользовать через `swap`, убрав пер-тиковые аллокации.

### H1.3 EGL/GL (`embedder/src/platform/egl_horizon.cpp`)

- `flutter_libnx_egl_present` каждый кадр зовёт `DrawCursorOverlay`, но та
  сразу выходит, если курсор невидим. Когда курсор виден: `eglQuerySurface` ×2
  + 5 GL-запросов состояния + 2 отрисовки `scissor/clear` + восстановление.
- `eglSwapInterval(1)` — кадр синхронизирован с Vsync.
- **Оценка:** мизер. Размер поверхности фиксирован (1280×720) — можно
  кэшировать вместо двух `eglQuerySurface` на кадр, но это не горячая точка.

### H1.4 Видео-путь media_kit (растр-поток) — **единственная реальная просадка**

`embedder/src/engine/media_kit_video_horizon.cpp`, кадровый коллбэк:

- На каждый видео-кадр: `mpv_render_context_render` + обнуление альфы
  (`Clear` на альфа-канале).
- **Каждые 120 кадров** (`render_count % 120 == 0`): `glReadPixels` из центра
  текстуры — **диагностика**. `glReadPixels` синхронизирует GPU-конвейер
  (столл) → микролаг примерно каждые ~2 с при воспроизведении видео.
- Логи в этом пути уже троттлятся (первые N + каждый 120-й).

**Рекомендация (I1):** убрать `glReadPixels` и связанные `LOG_INFO` из
нормального пути — выполнять их только при включённой отладке. Это не только
меньше логов, но и снимает реальный столл.

### H1.5 `switch_platform.cpp`

`PollEvents` каждый тик; логов, кроме init/shutdown/ошибок, нет. Чисто.

## H2. Подозрительные логи

Усилитель шума: `LogWrite` делает `fflush` **на каждую строку** (stdout и файл
на SD). Каждая лог-строка = синхронная запись. Это осознанный выбор (последняя
строка перед крашем — самая важная), но он делает объём логов прямо
«платным».

Легенда частоты: **тик** — каждую итерацию петли; **период** — раз в N кадров;
**событие** — на действие; **старт** — один раз при запуске.

| Место | Сообщение | Частота | Оценка |
|---|---|---|---|
| `main.cpp:164` | `Frames: …/s im Zeichnen …` | период (120 кадров ≈ 2 с) | полезно для H3, но шумно |
| `main.cpp:497` | `Taste nicht zugestellt (handled=0) - Fokus?` | событие (нажатие) | 14× за сессию `my_nexus` |
| `main.cpp:177` | `[engine:*] …` | событие (сообщения движка/фреймворка) | при старте может быть много |
| `media_kit…:749` | `render #N … ok` | период (120 кадров) | диагностика |
| `media_kit…:772` | `Pixel Mitte R=… G=… B=… A=…` | период (120 кадров) | диагностика **+ GPU-столл** |
| `media_kit…:722/789` | `Callback …` / `liefere Textur …` | старт (первые) | ок |
| `event_channel…:34/42` | `Stream geoeffnet/geschlossen` | событие | ок (редко) |
| `plugins…:329/702/730/800/806` | file_picker/image_picker/url_launcher | событие (действие) | ок |
| `thread_diag…:132` | `Heap-Scan[%s]: … +N KB type=… perm=…` | старт | **уровень `ERROR`** — 59 строк в `my_nexus` |
| `log.cpp:259` | (все строки) | — | `fflush` на строку (см. выше) |

### Что показал `build-logs/my_nexus.log`

| Уровень | Строк |
|---|---|
| INFO | 101 |
| ERROR | 59 |
| DEBUG | 14 |
| WARN | 6 |

- **59 `ERROR` — это построчные дампы `Heap-Scan[%s]`** (регионы, признанные
  «abweichend»), а не сбои. В обычной работе они создают ложную тревогу и
  раздувают счётчик ошибок.
- Топ повторов: `Taste nicht zugestellt` — 14×, `Frames:` — 8×,
  `[engine:flutter] … Failed host lookup … cartocdn` — 30× (сетевой сбой того
  прогона, см. `docs/horizon-tls-roots.md`).
- Объём: 201 строка (`.log`) и 137 (`.alt`) — умеренно; основное «мясо» —
  стартовые дампы и сетевые ошибки.

## H3. Замеры (железо)

### Наблюдения из `my_nexus.log` (2026-10-11)

- **FPS** (строки `Frames:`): 51.8, 46.3, 58.5, 59.5, 57.1 → обычно
  **55–60 fps** (Vsync 60 Гц).
- **Худший интервал между кадрами:** обычно 40–100 мс, единично **343 / 367 /
  403 мс** — заметные «залипания».
- **media_kit render/pixel: 0** — в этом прогоне видео не запускалось, поэтому
  H1.4 по логам не подтверждён (нужен прогон с видео).

### Наблюдения из `my_nexus.log` (2026-10-15, «сеть есть», DEBUG-сборка)

Прогон `my_nexus` на консоли; лог — файловая сенка (`stdout=0 nxlink=0 netz=0`).

- **Сеть полностью поднята.** `NETPROBE`: `backend.my-nexus.ru`, `my-nexus.ru`,
  `dns.google` — DNS OK, TCP 443 OK, RAW TLS OK, HTTP 200. То есть гипотеза о
  связи залипаний с падающим DNS **не воспроизвелась**: столлы есть и при
  полностью рабочей сети (см. ниже).
- **FPS** (22 отсчёта `Frames:`): мин **23.7**, макс **60.1**, в среднем ≈ **50**;
  есть группа ровных 60.0. Просадки до 23.7/27.8 совпадают по времени с потоком
  ошибок приложения (см. ниже).
- **Худший интервал:** от 17 до **479 мс**; ≥250 мс — в 11 из 22 отсчётов
  (479, 461, 459, 354, 350, 330, 323, 317, 260, 257, 251). То есть столлы
  крупнее прошлых 343–403 мс — но в этой сборке активна пиксельная проба
  (см. оговорку).
- **Видео не задействовано.** Ни одной строки `media_kit_video: Callback`/
  `render`, ни одного `Pixel Mitte` — при том что лог на `DEBUG`. Приложение до
  видеосцены, судя по всему, не дошло.
- **Ошибки приложения (не эмбеддера):** `MissingPluginException` по
  `com.llfbandit.app_links/events|messages`, затем сотни
  `Null check operator used on a null value`. Печатаются как `INFO` через
  перенаправление stderr движка (`main.cpp:177`); просадки FPS ложатся на этот
  поток.
- **Загрузка данных API снова падала при рабочей сети** (по сообщению о
  прогоне; в логе строк ошибки нет — это слепая зона, см. ниже). Отказ
  происходит **позже старта**: одноразовый `NETPROBE` на старте показывает
  DNS/TCP/TLS/HTTP 200, т.е. на тот момент стек рабочий. Кандидаты:
  транзиентная «сеть не готова» (вывод 2026-10-11, `horizon-tls-roots.md` §4),
  либо исчерпание пула BSD-сессий (16 — потолок; держать ≤4 параллельно,
  `flutter-app-integration.md` §3), либо app-side (авторизация/парсинг →
  тот самый поток `Null check operator`).
- **Почему ошибки API не видны в логе:** в release/AOT `Get.log`/`AppLogger`
  (GetX) молчат (`kDebugMode == false`), в SD-лог попадает только `print()`
  как `[engine:flutter]` (`horizon-tls-roots.md` §5). Чтобы диагностировать —
  нужен `print()` из API-слоя приложения.
- **Старт/куча штатно:** регионы `Heap-Scan` — `DEBUG`, сводки — `WARN`
  (`Start` 3/1, `nach EGL-Init` 37/18, `vor RunInitialized` 43/21, до 124 МБ).

> **Оговорка:** сборка сделана с `min_level=kDebug`, поэтому вместе с `Frames`
> работает и дорогая пиксельная проба `glReadPixels` (~раз в 2 с). Worst-gap в
> этом прогоне сопоставим со старым baseline, а не «чистый» (без пробы).

### Гипотеза к «залипаниям» 343–403 мс

В прогоне 2026-10-11 **все** резолвы тайлов падали (`Failed host lookup … System
busy`) — отсюда предположение, что резолв на главном изоляте даёт такие
интервалы. **Проверено прогоном 2026-10-15:** при полностью рабочей сети
(`NETPROBE` — всё OK) залипания 250–479 мс сохраняются. Значит **«сеть не
готова»/DNS-сбой — не причина** (по крайней мере, не единственная). Два
независимых источника:

1. **Приложение/плагины:** поток `Null check operator …`/`app_links` совпадает с
   просадками (webview + отсутствующие плагины, см. `plugin-plan-my-nexus.md`).
2. **Резолвер libnx под параллельной нагрузкой:** массовые `getaddrinfo`
   (плитки карты) всё равно упираются в лимит — независимо от того, «есть сеть»
   или нет.

Дополнительно загрязняет картину активная `glReadPixels`-проба в DEBUG-сборке.

### Протокол замера (для добивки на железе)

1. Снять логи `ui_app` (без видео) и `my_nexus` (с видео и без).
2. Зафиксировать: строки `Frames:` (fps + worst gap), наличие/частоту
   `media_kit_video: render` / `Pixel Mitte`, общее число строк и уровни.
3. Субъективная оценка плавности (перелистывание списков, карта, видео).
4. Сравнить «сеть есть / сети нет» — проверка гипотезы выше.

**Статус H3:** частично. Сделано: `ui_app` без видео (I2) и `my_nexus`
в сценарии «сеть есть» (2026-10-15). **Остаётся:** прогон `my_nexus` с
**реально запущенным видео** (в логе 2026-10-15 ни одной строки `media_kit_video`)
и сценарий **«сеть нет»**. Желательно — сборка с `DEBUG` для `Frames`, но без
пиксельной пробы, чтобы получить «чистый» worst-gap.

## Выводы → вход для I1

1. **Петля и EGL — чистые.** Оптимизировать нечего без замеров; правки в
   `TaskRunner`/`DrawCursorOverlay` — только при явных просадках (низкий приоритет).
2. **media_kit:** убрать `glReadPixels` и его `LOG_INFO` из нормального пути
   (диагностика только при отладке) — это и шум, и реальный столл.
3. **Логи-периодика** (`Frames:`, `Pixel Mitte`, `render #N`) → уровень
   `DEBUG`, чтобы не шуметь при обычной работе.
4. **`Heap-Scan` построчно на `ERROR`** (59 строк) → понизить уровень
   (сводка — `INFO`/`WARN`, регионы — `DEBUG`); иначе счётчик ошибок всегда
   «красный».
5. **`fflush` на строку** — оставить (осознанный выбор ради краш-логов); но
   снижение объёма логов из п.2–4 автоматически снижает и число записей на SD.
6. **Диагностика должна оставаться доступной** для отладки — то есть
   понижать уровень, а не удалять.

## I1 — что сделано

Реализовано на ветке `feat/log-noise` (набор «полный»):

1. **Уровень логов по умолчанию — `INFO`** (`LogConfig::min_level = kInfo`).
   `LOG_DEBUG` при обычной работе выключен; для отладки достаточно поставить
   `log_config.min_level = LogLevel::kDebug` в `main()` примера.
2. **Понижены до `LOG_DEBUG`** (шум периодики/событий):
   - `main.cpp` — отчёт `Frames: …/s` (был INFO, ≈ раз в 2 с);
   - `main.cpp` — `Taste nicht zugestellt (handled=0)` (14× за сессию);
   - `media_kit_video_horizon.cpp` — `Callback N` и `render #N ok`;
   - `event_channel_horizon.cpp` — `Stream geoeffnet/geschlossen`;
   - `thread_diag_horizon.cpp` — построчные регионы `Heap-Scan` (были `ERROR`.
3. **`Heap-Scan`-сводка** теперь `WARN`, только если есть отклонения; иначе
   `INFO` («keine Abweichungen»). Настоящие сбои сканера (`svcQueryMemory`,
   «Region rueckwaerts») остались на `ERROR`.
4. **Тяжёлая диагностика media_kit вынесена за debug-флаг:**
   `glReadPixels` в кадровом колбэк-пути выполняется только при
   `LogEnabled(kDebug)` — это убирает не только шум, но и реальный
   синхронизационный столл GPU каждые ~120 кадров.
5. **Новый хелпер `bool LogEnabled(LogLevel)`** (`log.h`/`log.cpp`) — чтобы
   дорогие диагностики не выполнялись впустую (одного `LOG_DEBUG` мало:
   аргументы/работа оцениваются до вызова).

**Проверка (сборка):** пересборка `ui_app` — 0 undefined, 0 дублей,
`ui_app.nro` 46M; все затронутые объекты перекомпилированы.

**Проверка (железо, I2):** `ui_app` на консоли, чистый старт → первый кадр →
выход. Единственная активная сенка — файл (`stdout=0 nxlink=0 netz=0`). Итог по
уровням: ≈35 `INFO`, 9 `WARN`, **0 `DEBUG`, 0 `ERROR`**.

- Построчные регионы `Heap-Scan` (прежде `ERROR`, до 24 строк на скан) в логе
  отсутствуют — на `kInfo` они `DEBUG` и подавлены.
- Периодика (`Frames: …/s`, `Taste nicht zugestellt`) не пишется — как задумано.
- Сводки `Heap-Scan` идут `WARN` при отклонениях: `Start` 3/1, `nach romfsInit`
  3/1, `nach EGL-Init` 37/18, `vor EngineInitialize` 37/18, `vor RunInitialized`
  43/21 (до 124 МБ) — это ожидаемые «наследованные» регионы при разогреве,
  не сбои сканера.

**Остаточный шум на старте (вне рамок I1; решение — оставляем как есть):**

1. 5× `WARN Heap-Scan … abweichend` — ложная тревога: отклонения здесь
   бенайнные. Вариант: bring-up-сканы на `INFO`, `WARN` — только при
   превышении порога (например, вне диапазона `main`-стека).
2. 4× `WARN MissingPluginException` по ядровым каналам (`flutter/isolate`,
   `flutter/keyboard`, `flutter/platform`, `flutter/navigation`) — эмбеддер их
   не обслуживает by design; вероятно, стоит понизить до `INFO`.

**Вывод:** снижение шума подтверждено на железе, регрессий нет. Полный прогон
для H3 (видео `my_nexus` + «сеть есть/нет», FPS/worst-gap) — отдельно.
